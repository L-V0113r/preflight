## Quick start for a judge

On Windows, double-click `Start PreFlight demo.bat`, then load the `extension` folder in Chrome (`chrome://extensions` → Developer mode → Load unpacked). On other systems, or to run each step by hand, follow [How to run it](README.md#how-to-run-it) in the README.

## The brief we started from

> Create a small local AI that runs alongside my browser, trained on finding malicious vulnerabilities (that hackers can exploit against a website user) within a website before the website is clicked on. When a link is pressed, the AI scans the website and, if anything is found, a pop-up appears before the website loads. Aimed at users who value extra privacy and can't risk anything happening, so extra loading time is acceptable. Code must be high-standard, commented, and modular, with home-made modules.

## Key decisions and why

| Decision | Alternatives considered | Why this one |
|---|---|---|
| **Local Python service + thin browser extension** | everything inside the extension (JavaScript ML); a cloud API | Python has the best ML tooling, and a local service keeps URLs private. Extensions can't easily do raw TCP, DNS checks or zip-bomb-safe decompression. |
| **Fetch the page ourselves, never execute it** | headless browser that runs the page | Running attacker code is risky and slow. Static reading is fast and safe. The cost (cloaking, run-time code) is documented. |
| **Hybrid: rules + ML + threat lists** | ML only; rules only | Rules give day-one precision and explanations. ML weighs weak signals. Lists catch known sites. The evaluation shows each part's contribution. |
| **Small gradient-boosted trees, not an LLM** | local or cloud LLM | Privacy, milliseconds of latency, no prompt-injection risk from page text, easy to evaluate and calibrate. |
| **Engineered features** | raw text / embeddings | Explainable, small, fast, and robust with modest data. |
| **Labelled synthetic training data** | scraping live phishing kits | Hackathon rules, safety and licensing. Loaders for real data are included for the next step. |
| **"Unsure" verdict** | binary safe/unsafe | A privacy-first user would rather be asked than falsely reassured. |
| **Standard-library HTTP server and fetcher** | Flask, requests | Fewer dependencies, and full control over security details (IP pinning, size caps, header checks). |
| **Closed shadow DOM for the pop-up, `textContent` only** | normal DOM injection | The page can't restyle, hide or script our warning. Evidence text from attackers can't inject HTML. |
| **Click interception in the content script** | `webNavigation` redirect to an interstitial page | Matches the brief ("when the link is pressed"), preserves new-tab and download behaviour, and is simpler to demo. Ctrl/Cmd-, middle- and Shift-clicks are checked and then opened as asked. Typed URLs and the right-click menu are documented gaps. |

## Build order

1. **Research** (see SOURCES.md): ClickFix, client-side/Magecart risks, drive-by compromise, browser-in-the-browser, cryptojacking, threat-feed access terms, Chrome extension messaging.
2. **Core types and config** (`schema.py`, `config.py`). Everything else agrees on these shapes.
3. **Safe network layer** (`net/`): SSRF guard with IP pinning, capped and decompression-safe reads, manual redirects.
4. **Parsing** (`parsing/`): domain helpers (registrable domain, look-alikes, entropy, edit distance) and a crash-proof HTML collector.
5. **Analysis and features** (`features/`): static JavaScript and text profiles, then 74 numeric features with a single source of truth for their order.
6. **Rule detectors** (`detectors/`): a tiny registry, then one module per area.
7. **Scoring and scanner** (`scoring.py`, `scanner.py`): noisy-OR, verdicts, notes, cache.
8. **Synthetic data, training, evaluation** (`data/`, `ml/`, `train_model.py`, `evaluate.py`).
9. **Local API with token auth** (`server.py`, `auth.py`) and the **extension**.
10. **Tests** (unit + end-to-end against a real local HTTP server), **demo site**, **docs**.

## What went wrong and how it was fixed

Each of these was found by running the system and reading its output. They are the most useful part of this document for a judge, and for anyone learning.

| # | Problem found | How it showed up | Fix |
|---|---|---|---|
| 1 | Search-box autocomplete detected as a keylogger | rules-only run: every synthetic web app flagged | "Sends data" now means a *strong* channel (`new Image().src`, `sendBeacon`) or `fetch`/`XMLHttpRequest`/`WebSocket` **to another site**. Same-site API calls are normal. |
| 2 | Developer docs with "copy install command" buttons flagged as ClickFix (CRITICAL) | designed hard-negative test | Clipboard-command is CRITICAL only if the command is hidden from the page text or the page shows "verify you are human / Win+R" instructions. Otherwise it's an INFO note. |
| 3 | Google Tag Manager's hidden `<noscript>` frame flagged as a hidden iframe | reasoning about real sites while writing the parser | Frames inside `<noscript>` (which can't run) aren't counted as hidden. |
| 4 | Honest pages with a bundle using `atob` in one script and `new Function` in another flagged as packed loaders | rules-only run on news/shop pages | Decode-then-run must happen **in the same script block**. |
| 5 | Articles *about* ClickFix flagged HIGH | security-blog hard negatives | Instructions without clipboard code are MEDIUM. With clipboard code they're HIGH or CRITICAL. |
| 6 | Company single sign-on flagged as phishing | SSO hard negatives | Known identity providers are allow-listed. Related domains (`acme-intranet` → `acme-identity`) get a LOW note. |
| 7 | An unreachable link rated **Danger** by the model alone | the failure-case demo | When the page can't be fetched and no concrete rule fires, the verdict is **Unsure**, and the model's link-only score is shown as a hint. Link-only model weight is reduced to 0.5. |
| 8 | Explanations said "few links" for pages that weren't even downloaded | the failure-case demo | Link-only explanations may use URL features only. |
| 9 | Shortcut learning: hyphens, link count, script size and brand mentions separated the synthetic classes too neatly | explanations + recipe-blog false alarm | Generator diversified (see [`readme/ai_techniques/06`](readme/ai_techniques/06_synthetic_data_and_shortcuts.md)). |
| 10 | "We accept PayPal" footers made honest login pages look like brand impersonation (26% false alarms on login pages, 5.5% overall) | per-family table in the full evaluation | Brand *claims* are read only from the `<title>` and `<h1>`/`<h2>` headings. Overall false alarms fell to under 1%. |
| 11 | The headline table made PreFlight look worse than the model alone | full evaluation | "Unsure" answers still stop the page, so they aren't misses. Added a "what the user experiences" table (opened silently / asked / warned) and a readable-pages-only table. |
| 12 | Too many pop-ups on honest sites: 13% of benign test pages stopped the user, almost all "Unsure" | the user-experience table | The model is calibrated on a 40%-malicious training mix, so it overstated real-world risk. Probabilities are now corrected to a 10% base rate (Bayes prior shift), and unreadable or unfamiliar pages are only questioned if something else looks off. Interruptions fell to 2.4%. The old behaviour is kept as the *Strict* setting. |
| 13 | Bot-protection and error pages judged as if they were the site | reasoning about Cloudflare's "Just a moment…" check, which resembles a fake-CAPTCHA scam | Only 2xx responses are analysed as page content (`FetchedPage.content_usable`). Anything else is treated as "couldn't read the page". |

## How it was verified

- `python -m unittest`: unit tests for URL tools, every rule (attack *and* honest look-alike), scoring logic and the model. End-to-end tests start a real HTTP server, scan every sample page through the real fetcher, check the SSRF guard, check that unreachable sites give Unsure and block-listed ones give Danger, check caching, and exercise the API's token and origin checks.
- `python evaluate.py`: the held-out synthetic study with baselines and leave-one-family-out (results in `backend/reports/evaluation_report.md`).
- The extension's JavaScript was syntax-checked with Node.js, then loaded unpacked and used in Chrome on the team's PC. There are no automated browser tests for it.

## Next steps (in priority order)

1. **Real-data evaluation.** Collect ~100 benign pages (Tranco top sites) and ~100 phishing pages (OpenPhish, within its terms) with `scan_cli.py --save-html`. Then run `evaluate.py --real-dir`. This is the number judges will ask for.
2. Retrain with that real data added (`train_model.py --html-dir`), keeping a separate real test folder.
3. Intercept typed URLs and bookmarks with an interstitial page (`chrome.webNavigation`).
4. Optional sandboxed rendering (headless browser in a container) for pages that look cloaked.
5. SHAP explanations; a full Public Suffix List; Firefox support.
